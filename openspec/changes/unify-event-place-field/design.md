## Context

予定フォームは場所名をAutocompleteで入力し、別の目的地欄に住所等を入力する。候補選択時には場所名、住所、Place ID、座標、Places typeを既存の予定データに保存し、経路検索ボタンは目的地の緯度・経度が揃っている場合に有効となる。Route APIは予定の座標とtypeをdestinationとして利用する。

## Goals / Non-Goals

**Goals:**

- 作成・編集フォームの場所入力と選択状態を共通化し、ユーザーに「場所」1項目だけを見せる。
- 自由入力文字列だけの予定を保存できるようにし、候補未選択ではRoute検索を使えないようにする。
- Places候補を選んだ場合は既存データ項目を保ち、住所と確定状態を明示する。
- 選択地点をその予定の経路検索destinationとして引き続き使う。

**Non-Goals:**

- Firestoreの新しいデータ構造、migration、APIまたはTransit検索ロジックの変更。
- Places Autocomplete以外のライブラリ追加やフォーム全体の再設計。

## Decisions

### 既存の予定フィールドを再利用する

場所の表示名は `location_name` に保存する。候補を選んだ場合だけ住所を `destination`、Place IDを `destination_place_id`、座標を `destination_lat` / `destination_lng`、typeを `destination_place_types` に保存する。自由入力の場合は文字列を `location_name` に保存し、候補に由来する値を空にする。これにより入力文字列と以前の座標が食い違う状態を防ぎ、既存のbackend request shapeも保つ。

### 選択後は読み取り表示に切り替える

候補を選んだ後は入力欄を選択済みの場所名・住所・チェック表示へ切り替える。「変更」操作で選択を解除し、表示名を初期値とするAutocompleteを再表示する。選択を解除した時点でPlace情報は保存対象から外れ、新しい候補を選ぶまで経路検索可能な地点として扱わない。

### 作成・編集のフォーム表示を共有する

同じ場所欄コンポーネントを作成と編集で使う。編集時は保存済み座標が揃っている地点を選択済みとして復元する。それ以外は既存の場所名、または住所を自由入力値として表示し、古いPlace情報を誤って保持しない。

### 経路検索契約は維持する

予定詳細の経路検索ボタンは現行どおり保存済みの緯度・経度が揃うときだけ有効にし、候補未選択時の案内も維持する。`App` がその予定の保存済み座標とtypeをRoute APIへ渡すため、APIやbackendを変更しない。Route検索画面の目的地表示には同じ予定の場所名を使う。

## Risks / Trade-offs

- 古い予定の表示名と住所を1つの自由入力値へまとめる際に、元の分離状態は編集保存後に失われる。開発中でmigration不要という要件に従い、場所の読みやすさを優先する。
- Places候補が位置情報を返さない場合は選択状態を示せるが、検索ボタンは座標条件により無効のままとなる。

## Migration Plan

Firestoreのmigrationは行わない。候補選択時は既存フィールドを保存し、自由入力で保存した予定は文字列を `location_name` に、Place由来項目を空にする。
